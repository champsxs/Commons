# Commons

An internal registry where teams define datasets, reuse and link to each other's data, upload files, and query everything through one GraphQL API.

**Status:** Milestone 1 (backend core) is done. The web app, UI kit, pages-as-code, CLI and MCP server come next (M2–M4).

## Run it

Requires Docker, Node 22+ and pnpm.

```bash
pnpm install
pnpm db:up        # Postgres 17 + MinIO
pnpm db:reset     # create the schema and load sample data
pnpm dev          # API on http://localhost:4000, GraphiQL on /graphiql
pnpm test         # integration tests (uses the commons_test database)
```

Sample data: three users (alice is an admin, bob and carol are in Retail Operations) and four linked datasets:
`countries` ← `cities` ← `stores` ← `monthly_sales`.

Get a token for trying the API (dev mode only):

```bash
curl -s -X POST localhost:4000/api/auth/dev-token -H 'content-type: application/json' -d '{"email":"carol@example.com"}'
```

## How it works

- **Registry** (`commons` schema): datasets, fields, links between datasets, teams, sharing, ingest history, audit log.
- **Datasets** become real tables in the `data` schema. A *reference* field becomes a foreign key (`city` → `city_id`) plus a link record, so the registry knows who uses what.
- **GraphQL** is generated by PostGraphile v5 from the `data` schema and rebuilt whenever a dataset changes. References appear in both directions: `store { city { country } }` and `city { stores }`.
- **Permissions** use Postgres row-level security. Every request runs as the `commons_user` role with the caller's id, and each table's policies call `can_view_dataset` / `can_edit_dataset`:
  - `private`: owner and owning team
  - `shared`: plus the teams/people it's shared with
  - `company`: everyone
- **Ingest** accepts CSV, JSON or JSON Lines. It validates values, resolves reference codes (`STO`) to row ids in one lookup per field, and reports unknown codes. Modes: append, upsert (on the key field), replace. Options: dry run, skip bad rows, and what to do with unmatched references (reject, skip, leave empty).

### Safety rules between datasets

- You need view access to a dataset to reference it (FK checks bypass RLS, so this stops probing private data), and owners can mark datasets as not referenceable.
- References can only target unique fields.
- Deleting a referenced row is blocked (`restrict`) unless the referencing owner chose `set_null`; nothing ever cascades into someone else's data.
- A field other datasets match on can't be dropped, and a dataset others reference can't be deleted.
- API tokens are scoped (`data:read`, `data:write`, `datasets:write`, `pages:write`); GraphQL depth is limited; page tokens are read-only unless the page is allowed to write.

## API overview

| | |
|---|---|
| `GET /api/search?q=` | datasets, fields, pages |
| `GET/POST /api/datasets` | list / create |
| `POST /api/datasets/suggest` | similar datasets and likely references for a proposed dataset |
| `GET/PATCH/DELETE /api/datasets/:slug` | details (incl. generated GraphQL names), settings, sharing |
| `POST/PATCH/DELETE /api/datasets/:slug/fields[/:name]` | add, describe/deprecate, remove fields |
| `GET /api/datasets/:slug/usage` | datasets and pages that depend on it |
| `POST /api/infer` | guess fields from an uploaded file |
| `POST /api/datasets/:slug/ingest` | upload a file |
| `GET /api/graphql/schema.graphql` | the current GraphQL schema |
| `POST /graphql`, `GET /graphiql` | GraphQL |
